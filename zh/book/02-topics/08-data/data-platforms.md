# 数据工程导读：从业务约束到架构决策

Last updated: 2026-10-21

看板上的一个"日活"数字，背后可能经过了十几个系统：手机里的埋点 SDK、接入服务、消息队列、对象存储、批处理和流处理引擎、数据仓库的分层表、指标定义、调度系统、权限系统。任何一环出错，这个数字都会悄无声息地变错。

这组文章不按工具逐个讲解，而是沿着一条因果链展开：

> **业务需求决定设计目标，设计目标决定架构权衡，架构权衡决定技术选型；技术的限制又反过来约束产品能做什么。**
> ——曹犟，《大数据应用实战》第 01 讲

本文是这组文章的入口：说明六篇文章各回答什么问题、按什么顺序读，以及贯穿全系列的六个设计目标和五个核心权衡。具体机制都在对应文章里，这里只给地图。

## 前置知识

- 能写 Python 和 SQL，理解 HTTP 请求与关系数据库的基本用法
- Stage 1 的 [SQLite](/zh/book/01-quick-start/05-api-data/sqlite) 与 [后端入门](/zh/book/01-quick-start/05-api-data/backend-intro)

## 学完这组文章，你应该能

- 解释一个指标是从哪里来的，经过了哪些加工
- 让一条数据管道在重试、迟到数据和上游变更下保持正确
- 为系统的时效性、恢复能力、安全和成本选择给出理由，而不是"大家都这么用"
- 解释几家大厂的数据平台为什么长成今天的样子，把任何一个云数据产品拆回到机制
- 规划自己学什么、用什么，并在生态持续变化时保持判断力

## 二、六个设计目标：贯穿全系列的透镜

动手设计之前，先回答六个问题。它们的答案决定后面几乎所有选择。

| 设计目标 | 要回答的问题 | 答案如何改变架构 | 在哪里展开 |
|---|---|---|---|
| **数据类型** | 只有日志、业务表这类结构化数据，还是也有图片、视频、评论？ | 结构化数据适合列式存储和 SQL；非结构化数据需要对象存储和更灵活的处理方式。大模型的多模态能力让非结构化数据第一次变得"可分析" | [[数据系统的构成]] |
| **数据量** | 单机放得下吗？未来三年会增长多少？ | 超出单机就必须水平扩展。2003 年起 Google 的 GFS、MapReduce、Bigtable 论文和随后的 Hadoop 生态，让 TB/PB 级处理不再是巨头特权 | [[数据库基础与大数据演进]] |
| **时效性** | 数据从产生到可用，能容忍多久？ | 天级报表用批处理即可；推荐和广告要求秒级甚至毫秒级，需要流处理和预计算。时效性越高，成本和复杂度越高 | [[数据系统的构成]] |
| **成本** | 硬件、软件授权、开发和运维，各占多少？ | 摩尔定律降低了单位硬件成本，但数据量和时效性要求的提高抵消了这部分红利。开发和运维成本同样不能忽略 | [[数据系统的构成]]、[[数据平台运维]] |
| **安全与隐私** | 哪些数据敏感？谁能访问？法规要求什么？ | GDPR、个人信息保护法这类法规要求从设计第一天就考虑保护，并贯穿采集、传输、存储、计算、应用全链路 | [[数据平台运维]] |
| **可维护性** | 系统上线三年后还有人能维护吗？ | 建设期通常资源充足，大多数系统是在长期运行中因缺乏维护而逐渐不可用。分层、血缘、质量监控和生命周期管理都是为此服务的 | [[数据治理]]、[[数据平台运维]] |

这六个目标经常相互冲突：时效性和成本冲突，安全和易用冲突，数据类型的多样性和可维护性冲突。所以下一步是做权衡。

## 三、五个核心权衡：立场与前提

下表给出一个典型分析型数据系统（服务于报表、用户行为分析、推荐）的常见立场。**每个立场都有前提**，前提变了，立场就该变。

| 权衡 | 典型分析系统的常见立场 | 这个立场成立的前提 | 在哪里展开 |
|---|---|---|---|
| **一致性 vs 可用性** | 网络分区时优先保持可用，接受副本之间短暂不一致，以最终一致为目标 | 下游是决策支持和推荐这类能容忍短暂不一致的场景。库存扣减、资金结算不在此列 | [[数据库基础与大数据演进]] |
| **批处理 vs 流处理** | 批流一体：流处理满足新数据的时效性，批处理负责历史数据和修正 | 两条路径的业务口径必须一致，否则会出现"实时数和离线数对不上" | [[数据系统的构成]] |
| **事务处理 vs 分析查询** | 以 OLAP 和列式存储为主 | 查询以大范围聚合为主，很少更新单行，不需要强事务 | [[数据库基础与大数据演进]]、[[数据系统的构成]] |
| **数据质量 vs 处理速度** | 主干路径只做不影响速度的轻量校验（格式、范围），重度校验放在旁路异步进行，发现问题后隔离或修正 | 下游能接受"先到达、后修正"。对账类场景需要反过来，先校验再发布 | [[数据系统的构成]]、[[数据治理]] |
| **成本 vs 性能** | 没有统一答案：对象存储便宜但慢，SSD 快但贵；弹性资源灵活，预留资源便宜 | 取决于访问频率、峰谷差异和团队运维能力 | [[数据系统的构成]]、[[数据平台运维]] |

一个容易被忽略的原则：成本、可靠性、时效性三者之间可以折衷，**安全合规不能折衷**。必要时为安全合规增加成本，是合理的工程决策，而不是浪费。

## 四、七层是地图，不是清单

把数据从产生到使用的路径拆成七层，是为了分离关注点：每一层只解决一个问题，可以独立演进、独立替换。

| 层 | 解决的问题 | 一句话要点 |
|---|---|---|
| 数据源 | 数据从哪里来 | 系统之外的各种异构来源：App 埋点、服务日志、业务数据库、第三方接口 |
| 采集 | 如何捕获 | 不同数据源用不同采集方式，格式和时间戳在这里统一 |
| 接入 | 如何接收并初步处理 | 批处理数据写入存储；流式数据可以跳过存储直接进入计算 |
| 传输 | 如何不丢、不压垮下游 | "数据高速公路"，提供缓冲、解耦和重放能力 |
| 存储 | 如何高效、低成本地保存 | 离线系统的核心；冷热分离、读写分离这类复合设计已成为主流 |
| 计算 | 如何大规模加工 | 两重职责：加工数据并写回存储，以及直接满足应用查询；需要在存算一体和存算分离之间选择 |
| 应用出口 | 如何被使用 | 抽象成三类：给人用的**产品化界面**（BI、看板）、给其他系统用的 **OpenAPI**、给 AI Agent 用的 **MCP 协议** |

每一层的机制和选型见 [[数据系统的构成]]。各家大厂在每一层对应的产品，以及 Google、AWS 的同类产品，见 [[大厂数据平台与实践案例]] 第三节的产品矩阵：七层是机制的地图，也是读懂任何一个云数据产品的坐标系。

## 五、最后两篇：从机制到行业，从行业到个人

前四篇只讲机制，需要时引一两句真实经历。完整的企业故事和行业格局集中在第五篇 [[大厂数据平台与实践案例]]，它做两件事：

- **横向比较**：阿里、字节、腾讯、百度、华为的数据平台各是被什么业务逼出来的，各家产品怎样对应前四篇的机制，和 Google、AWS 有什么不同，2026 年各自走到了哪里，在 AI 时代押注什么；
- **纵向案例**：百度从 Log 平台到 UDW、一家独立行为分析厂商的十年、一家中型互联网公司的三次存储升级、一家银行的调度改造等六个案例，每个都标明它印证的是前四篇的哪个机制。

最好读完前四篇再读它：你会发现每家公司的选择，都能用这里的六个设计目标和五个权衡重新推导出来。

第六篇 [[数据工程师的成长地图]] 把视角从行业转回个人：用一张六级能力阶梯定位自己，按三层知识的半衰期分配学习时间，按场景而不是按热度选平台，并把每年几百条厂商公告翻译成"改了哪一层的哪个取舍"。它的主张贯穿全系列：**产品会变，机制变得很慢；专家的标志是能从约束推导出方案。**

## 六、怎么读

| 读者 | 建议路径 |
|---|---|
| 数据开发工程师 | 按顺序读完前四篇并完成每篇的练习（练习是检验理解的标准，不是附录），再读第五篇的产品矩阵，最后用第六篇规划下一步 |
| 后端工程师（转向数据） | 先读第二篇的传输层和计算层，再回到第一篇补 CAP 与存储引擎，然后读第三篇的 ETL 幂等性 |
| 产品经理、数据分析师 | 读本文、第二篇的第一节和最后的端到端流程，再读第三篇的指标口径和数据质量。目标是理解系统的约束，提出有成本意识的需求 |
| 技术管理者、做平台选型的人 | 先读本文和第五篇的上篇（大厂对比与产品矩阵），再按需回到第二篇的计算选型和第四篇的部署方式 |
| 想规划成长路线的数据工程师 | 读完前五篇后读第六篇；也可以先读第六篇第一节，用能力阶梯给自己定位，再按缺口回到对应的文章 |

对数据的使用者来说，理解技术设计的意义在于**提出合理的需求**：知道一个"实时"需求会让成本上升多少，知道一个口径变更会影响哪些下游报表。对开发者来说，这张地图是面对新需求时的起点：先在框架里定位，再按自己的业务裁剪。

## 思考题

1. 除数据系统外，你还接触过哪些复杂系统？它们做设计取舍的依据是什么？
2. 你工作中的数据系统符合本文的七层划分吗？如果不符合，是出于什么考虑？
3. 在你的场景下，第三节五个权衡的立场分别应该是什么？哪一个前提最可能在未来一年被打破？
4. 你现在用的几个数据产品，分别落在第四节七层里的哪一层？其中哪一个，你说不清它的数据存在哪里、用什么格式？
